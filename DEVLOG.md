## Blu-ray movies decrypted (Nov 10)
- src/core/aacs.c: the disc ID is the SHA-1 of AACS/Unit_Key_RO.inf; its KEYDB.cfg entry ("0x<ID> = <title> | V | 0x<VUK> | U | 1-0x<key> ; ..." fields in any order) gives the VUK, which opens the unit keys in that file (a BE32 to the key block, a BE16 count, each key 48 bytes on, AES-128-ECB), or the unit keys outright. The m2ts files under BDMV/STREAM are encrypted in 6144-byte units from each file's start: the clear first 16 bytes, AES-encrypted with the unit key and XORed with themselves, are the key for AES-128-CBC over the rest (IV 0BA0F8DD...0F78), and only units with the copy permission bits set (0xC0 of the first byte) are; after, those bits are cleared, as libaacs does. A unit that doesn't come out as transport stream packets (0x47 every 192 bytes) is tried with the disc's other unit keys, and fails the rip with none.
- A Blu-ray movie's ISO rip goes through a reader that decrypts the streams as they're read (like DVD's CSS), the files' extents from UDF 2.50, runs that follow on the disc joined (a UDF extent is at most 1 GiB less 2 KiB, not a whole number of units). Without the key the ISO is the disc as it is, and the note says so with the disc ID.
- Checked: our unit encryption against openssl's AES from the spec (same SHA-1), and libaacs 0.11 (Debian bookworm's) opening a synthetic disc folder with a KEYDB.cfg holding its VUK and decrypting the unit to the same bytes. libaacs wants Unit_Key_RO.inf over 2048 bytes with an application type and a BDMV folder count in its header, which real discs have; the tests' file has them now.
- Settings: Blu-ray Keys under Keys, <data>/keys/KEYDB.cfg by default, the count of discs in it counted once per version of the file (a full one is tens of MB).
- Not handled: AACS 2 (4K discs, bus encryption), BD+. Not tried on a real disc yet.
- 4K: OmniDrive's own table marks UHD-BD "native" (read as the stock firmware does), not unlocked; LibreDrive is what turns bus encryption off, and only MakeMKV turns it on. The open question is whether OmniDrive's raw read (C0) comes before bus encryption. The drive test now looks: on a Blu-ray movie it reads AACS/Content000.cer (type 0x10 is AACS 2, the top bit of byte 1 bus encryption, as libaacs's content_cert.c), then the largest stream's first unit with READ(12) and, on OmniDrive, with C0 (descrambled, EDC checked), and says what each gave: the unit's clear head (AACS data, no bus encryption), plain video, zeros, or scrambled from the first byte. The fake drive can raw-read any Blu-ray now (nintendo = 3) and garble READ(12) over a range, as bus encryption would.

## Common formats and defaults (Nov 9)
- Each disc type's default is now what its players most commonly take: Wii WBFS, PS2 ISO (OPL needs it, PCSX2 and PS5SX2 read it; was CHD), Xbox XISO (xemu and modded consoles; was the full ISO). PS2 CD games can be ripped as an ISO too (2048-byte sectors through the reader, untried on a real disc). Audio CDs can be ripped as BIN/CUE to burn a copy (the CD path already applies the drive's read offset to audio tracks).
- XISO (src/core/xiso.c): the game partition found at 0 (already an XISO) or Redump's XGD1/2/3 offsets (0x18300000, 0xFD90000, 0x2080000), by the volume descriptor at sector 32; cut after the last byte any file or directory table uses (a walk of the XDVDFS trees, with a visit limit so a looping tree is refused). extract-xiso 2.7.1 lists and extracts a converted synthetic image (the same files, the right sizes) and can't read the full Redump-layout one.
- CISO (src/core/ciso.c): Nintendont's layout (kernel/ISO.c): "CISO", the block size LE (only 2 MiB is accepted), a byte per block, the stored blocks from 0x8000. Used blocks: the header, bi2 and apploader (0x2440, its size and trailer), the DOL's 18 sections, the FST and every file in it. Dolphin reads the same header.
- WBFS (src/core/wbfs.c), now the Wii default: one disc, 512-byte hd sectors, 2 MiB WBFS sectors, 4482 block entries (286864 Wii sectors / 64, as wit and USB Loader GX's libwbfs), the disc header copy and block table at byte 512, the file cut to n_hd_sec x 512 (Dolphin checks it). Used blocks: block 0 and each partition from its start to data_offset + data_size (0x2B8/0x2BC of its header). Nothing is decrypted, so no Wii key is involved; against a scrubbed copy it keeps what's unused inside each partition, and the update partition (USB Loader GX drops it). Split for FAT32 (on by default): 4 GiB - 32 KiB parts, X.wbfs, X.wbf1..., at most 10. Laid out as USB Loader GX looks for it: "<name> [ID6]/ID6.wbfs". Checked with wit 3.05a on a properly encrypted, fake-signed image wit composed: wit verify OK, wwt check clean, copied back to an ISO identical to the original (split too), and the same mapping as wit's own --wbfs output. Not yet on a Wii.
- RVZ (src/core/rvz.c), for Dolphin: 128 KiB zstd chunks at level 5 (Dolphin's default), the pseudorandom padding stored as its seed (Dolphin's seed recovery, on 32 KiB blocks, with the GameCube FST for padding that starts mid-block), repeated-byte chunks shared, zero chunks free, the header and table SHA-1s Dolphin checks. Byte-identical to dolphin-tool's own RVZ (master 41799046) of the same image: a full-size synthetic GameCube image (1.46 GB to 313 MB), an NKit Animal Crossing image and the test image; dolphin-tool converts each back to an ISO with the input's SHA-1. Levels 1 and -5 identical too; at 22 about 1 KB apart, from zstd 1.5.5 against Dolphin's bundled 1.5.8. Wii goes as raw data with no partition entries, which Dolphin reads (and writes itself for partitions it doesn't decrypt), so it's about the ISO's size: packing it needs the partitions decrypted, so the Wii common key. 5 MB of memory.
- Both are written from the ISO as read, which is then removed; the manifest keeps the read image's hashes (Redump's).
- Dreamcast CHD put off: chdman 0.264 (the PC's) writes GD-ROM CHDs as CHGD metadata with values that don't follow from MAME's published parse_gdi (a synthetic three-track GDI gave track 1 PAD:-4 and track 3 FRAMES:1009 from a 1,003-frame file), and Flycast reads those values as they are. Also seen: that chdman misreads a quoted GDI file name that has no space in it (the loop that joins the name's parts never sees the closing quote); ours always have " (Track N)", so they're read right.

## Deathloop on ShadowMountPlus: the left-out languages (Nov 9)
- The fake-signed exFAT dump registered with ShadowMountPlus (image-backed, 72.8 GB, saves kept) with the installed game deleted and the disc out. It launched and crashed the same way twice: eboot.bin ran, graphics up, libSceSaveData init, then SIGSEGV writing to 0 at 0x1b5281c. That's the game's own fatal routine (`movl $0x12345678, 0x0; ud2`), reached through a virtual call right after it loads base/initfiles.index, which names elid_<language>/srinfotable for all ten languages. Six of those folders had been left out. (Read from the console's klog on port 3232 and the decrypted eboot, base 0x400000, text at file offset 0x4000.)
- The installed game gets away with it because the files are there with no data behind them: it opens every language's srinfotable but reads only its own. So a dump keeps left-out language folders as stand-ins: every folder and file, each its real size, empty (ftruncate, sparse on the console). Nothing of theirs is ever read.
- What's left out, in two steps: the languages the copy doesn't have (other regions'); if that doesn't account for what's missing, the copy's optional languages too, all but its main one (chunkDefaultLanguage), since which of them were installed can't be told apart (Deathloop's ten folders are all 0.22 GB). The note says which: "Left out German, ..., which this copy of the game doesn't include." or "Kept English only. French, ... weren't all installed: add them in Manage Game Content and rip again to include them." Anything else missing still refuses.
- Complete Dump (a dump option, off by default), for preservation: every file or nothing. With anything missing it stops before starting the game and says why.
- Other tools: itemzflow asks for every language to be installed first; EchoStretch's ps5-app-dumper reads plainly (would hang on Deathloop). None found that writes stand-ins.
- The languages weren't it. The folder dump with all ten language folders (job 7, fake-signed, /data/homebrew/PPSA01302) crashed at the same place: rip 0x1b5281c, backtrace 0x156dc79 <- 0x14fe776 <- 0x4000bf. The function there calls scePlayGoInitialize (a 2 MiB heap), then scePlayGoOpen, then scePlayGoGetChunkId, and sends every PlayGo error (0x80B20003-0x80B2000E, a jump table at 0x36667d8) to the fatal routine. initfiles.index is only loaded just before it. A game run from a folder or image has no PlayGo behind it (ShadowMountPlus mounts with playgo=0, and nothing was installed), so Open fails.
- The fix people use: drakmor's pgo_stub, a libScePlayGo.sprx that answers every chunk as installed (GPL-3.0, release 0.6, 18,150 bytes). ShadowMountPlus overlays it for folder and image games when it's in /data/shadowmount/emus (beside libSceAmpr.sprx, which was the only one there). It reads an optional /app0/playgo_stub.dat: chunk count or list, scenario count, then a language mask or list; with no file, 1000 chunks and every language.
- ShadowMountPlus only takes /data/shadowmount/emus files to update ones a game's fakelib already has (a backport's, the game folder's own fakelib/, or the global /data/shadowmount/fakelib, empty here). It never adds them: with nothing there, the system's libScePlayGo loaded (same fingerprint, a01c0e5d...). With fakelib/libScePlayGo.sprx in the dump: pgo_stub loaded (d6e695d1...), PlayGo passed, and the game stopped at the next step: sceKernelAprResolveFilepathsWithPrefixToIds("/app0/base/", ...) (eboot 0x400450, from 0x158eb48) gave 0x80020019 (ENOTTY), also fatal (0x158ebf1). The system's APR can't resolve files on a folder mount.
- With fakelib/libSceAmpr.sprx added too (drakmor's ampr_emu 0.4.2.1, which does its own sceKernelApr*): Deathloop launches, from a fake-signed folder dump with stand-in language folders, the disc out and the installed game deleted. The emulator writes ampr_emu.index into the game folder on first run (it reads /app0/ampr_emu.index, and logs to /app0/ampr_emu.log when built with logging).
- So the language folders were never what crashed it. Whether the stand-ins are needed at all is untried (a dump without them, with both emulators).
- itemzflow's dumper (libdumper) handles PlayGo only for PS4 (playgo-chunk.dat, .sha and playgo-manifest.xml from the package, into the GP4 for a fake PKG) and lists "PlayGo Related Issues" as open; nothing for PS5 dumps. A PS5 dump that calls PlayGo or AMPR strictly needs the emulators from the loader side (backports often carry them in fakelib/).
- On the console (payload 20261110-044501): ASTRO's PLAYROOM (PPSA01325) dumped as a folder, 28,190 MiB from the -app0-patch0-union mount in about 11 min, 4 executables decrypted, fakelib/ with both emulators taken from /data/shadowmount/emus. Its contentVersion is 01.905.000 as installed, but that's the preinstalled app's own: /user/patch/PPSA01325 is there and empty, so no update was involved and the update path is still untried. Not booted from the dump yet.
- ASTRO's PLAYROOM from that dump runs through ShadowMountPlus (folder, fakelib applied), after two snags:
    - Not on the home screen at first: the installed copy had been deleted, but as a preinstalled title its 2022 app.db record stayed, and ShadowMountPlus's registration landed on it. Uninstalling through ShadowMountPlus (/api/v1/games/uninstall: the registration only, the folder stays) and scanning again registered it fresh, and it showed.
    - Then "PRX_PROCESS_STARTUP_FAILURE": rtld refused fakelib's libSceAmpr.sprx ("mount flag / attribute error", va_mode 0x1a4). The dump wrote the emulators 0644; Deathloop's, sent over FTP, were 0777. Made executable (SITE CHMOD 777 here, chmod 0755 in add_emulators from now on), it started. ShadowMountPlus's fakelib cache key has st_mode in it, so the cache followed.
- So every PS5 dump now carries both, in fakelib/ (third_party/ps5-emulators: pgo_stub 0.6 and ampr_emu 0.4.2.1 as released, GPL-3.0 like RipperPS, built into the payload with embed.py --raw, about 440 KB a dump). The copies in /data/shadowmount/emus win when they're there, since ShadowMountPlus keeps those current and would put them over the dump's at launch anyway. PS4 games don't get them.
- With languages left out, the dump also gets playgo_stub.dat: pgo_stub's defaults (1000 chunks, 5 scenarios) and only the languages kept ("english_us,english_gb" for Deathloop's English-only dump), so the game isn't told it has languages that are only stand-ins.
- A firmware check was weighed and dropped: a dump comes from a game installed on the same console, so it always runs there without a backport. It only matters on another console, and the rip can't know which.
- Space: the PS5 reports about 28 GB more free than it lets be written. An exFAT image of Deathloop (job 6) ran out at 61 of 72.7 GB with "free" space to spare, since the image is built beside the dump (2x the game). A dump now checks for 1.1x the game per copy up front.

## More formats (Nov 9)
- Goal: every format a game's targets run, real or emulated (docs/development.md, Roadmap 1-6). Research for the PS4 fake PKG, CSO/ZSO, PBP, VCD and classics wrappers going on beside this.
- PS4/PS5 dumps read the system's -app0-patch0-union mount when it's there: the game as it runs, with the installed update over the disc's files. The system mounts it with no update too (Deathloop has none: /user/patch holds PPSA01325, CUSA06122 and CUSA01728 only), so it's always the one to read. The update's own .pbm/.pkg pairs (/user/patch/<id>, and on extended storage) count toward what's missing. The rip's note says "With update <contentVersion>." when the union's param.json differs from the disc's. Not tried on the console yet (it needs a game with an update installed, PPSA01325 for one).
- PS3 game folder (Game Folder, for RPCS3 and PS3 loaders): the decrypted image's files extracted (iso_extract: Joliet names, which PS3 discs carry; files over 4 GiB in several extents joined; "." "..", "/" names never written), then the image deleted. Without the disc's key it fails, since there's nothing to extract from an encrypted image. Tests: a hand-built image with a Joliet tree, a two-extent file and a ".." name; the PS3 rip test as a folder with and without a key.
- iso_mount now carries on past the primary descriptor to find a Joliet one, and takes descriptors that end without a terminator.
- PS3 ISO split for FAT32 drives (Split for FAT32 Drives, off by default): webMAN's and IRISMAN's parts, <name>.iso.0, .iso.1... of 0xFFFF0000 bytes (webMAN file_copy.h, IRISMAN file_copy.h), in a folder of their own (webMAN scans one level of subfolders of PS3ISO). An image that fits stays whole. RPCS3 can't read split images (it takes one ISO from v0.0.40, or the folder), hence off. The first part is the image renamed and cut, so only the rest is copied; a failure leaves the image whole. webMAN doesn't read exFAT by itself (prepISO does that), so FAT32 is what splitting is for.
- DLC: what's mounted while the game runs as /mnt/sandbox/pfsmnt/<content ID>-ac is dumped into "<name> (DLC)/<content ID>/" beside the game, with its icon from /user/appmeta/addcont/<id>/<label>/, and goes wherever the game goes. A DLC whose ac.pkg isn't all on the console (its ac.pbm) is left out. Entitlement-only DLC is never mounted: nothing to dump, and it keeps working on the same console. No loader mounts DLC from a folder yet (they install it as a PKG), so this is for keeping, and for the fake PKG writer later. The note says "With N DLC.". Not tried on the console (it needs a game with DLC that carries data).
- Research (scratchpad reports, not in the repository): PS4 fake PKG (LibOrbisPkg is LGPL-3.0; the format in full; ~2,500-3,000 lines; part of the key material is leaked Sony debug keys, which Alembic downloads rather than ships), PS5 fake PKG (LibProsperoPkg, ps5-ultrapack; firmware up to 11.60 reportedly), CSO v1/ZSO (PCSX2, PS5SX2, OPL, PPSSPP; 250-400 lines), PBP (emulators only without Sony's launcher), VCD (POPStarter; the user supplies POPS_IOX.PAK). Classics wrappers need Sony's emulator binaries, so not those: PS5SX2 (a PCSX2 port running on the PS5, reads iso/chd/cso/zso from /data/PCSX2/games or USB) and RetroArch/PSXS5 cover PS2 and PS1, as destinations rather than formats.

## Movies to MKV/MP4 (plan, Oct 26)
- Wanted: a DVD (and later Blu-ray) out as MKV and MP4, not just ISO, so it plays on other devices too.

- Built (Oct 26):

## The slow MP4, solved (Oct 26, ~03:45)
- Not the encoder and not the console. FFmpeg was opened with AVFMT_FLAG_GENPTS. Twine's cells each start their clock over (cell 5's is 408.8 s behind the title's timeline), and where they do, genpts looks for a later packet with a higher DTS to give a PTS to the ones without. None comes until the new cell's clock catches up, so it read hundreds of MB ahead (530 MB at cell 5) and rescanned the whole buffer for each packet: quadratic work and growing memory, with speed falling all the way. Reproduced on the PC with the full decrypted Twine ISO (copied off the console) and a harness around remux_title, with timing every 10 s and a packet trace (pos, cell, DTS) to find it.
- Without genpts, about one packet in twenty has a DTS and no PTS:
    - MP4 (re-encoded): only the last frame out of the filter had no PTS, and x264 then gave the muxer an invalid DTS. A frame without one now follows the one before by a frame.
    - MKV (copied): Matroska refused those packets (13,170 of them, all real frames). They're filled after fix_ts() has made the clock continuous: audio and subtitles take their DTS, MPEG-2 B-pictures too, and an I- or P-picture takes the next I- or P-picture's DTS (a queue of at most 64 packets; the picture type from the header after 00 00 01 00).
- On the PC, 16 cells (36 min, 1.6 GB) to MP4 at x264 ultrafast: a steady 18 to 22 MB/s, where it used to fall from 17.8 to 5.3. MKV: 6 s. Video and audio stay level, 51,910 frames either way. The `ffmpeg -f null` decode of the MKV prints some "non monotonically increasing dts" lines, as the old output did; they come from decoding the soft-telecined MPEG-2.
- Not yet on the console: the console went down before the build with this fix could be sent.

## Discs for custom drive firmware (Oct 27, night, not on hardware yet)

## MKV audio gap at cell boundaries (Oct 27)
- The "audio runs 4 min long" from Oct 26 was worse than that. Read back over FTP with ffprobe, every packet of Twine.mkv: video and the English AC-3 are in sync wherever there's audio, but the audio is missing from 2538.65 s to 2912.05 s (6 min 13 s of nothing), and the last audio packet sits at 7928.1 s, 248 s after the last frame. The packets add up to 7307 s of audio for 7680 s of video.
- The log of that rip has "cell 19's clock is -373.371 s off" at 2538 s and "cell 53's clock is -247.745 s off" at the end: the same two numbers.
- Cause: where a cell restarts the clock, an AC-3 frame that began in the cell before comes out of the demuxer after the new cell has been lined up (the parser only finishes a frame when the next audio packet arrives). It still has the old cell's timestamp, so the new cell's offset puts it 373 s ahead; then fix_ts's "never go backwards" drops every real audio packet until the clock gets there.
- First try: take the cell before's clock when the new one puts a packet outside its cell. That fixed the English track but not the two unlabelled stereo ones: at cells 2, 9 and 17 the jump (39.8, 173.2, 235.8 s) is shorter than the cell, so the leftover frame landed inside the cell on the new clock and swallowed that much audio behind it.
- Fix (remux.c fix_ts): each stream keeps the offset it's on while its own timestamps carry on (under 1 s from its last packet); a stream whose clock jumps takes the cell's. A cell is lined up by the first jump of an audio or video stream that was playing as the cell began (not by a subtitle, nor by a track coming back from silence). A jump that lands more than 3 s outside its cell is a stray and is dropped alone.
- Checked on the PC (harness around remux_title, Alpine's FFmpeg 6, the full Twine ISO copied off the console): all three AC-3 tracks 240,018 frames (7680.6 s) with no gap, all 184,153 video frames, every stream 2:08:00. - Left: one repeated video DTS at 448.93 s when the MKV is copied (from the I/P-picture DTS fill, not this).
- On the console (build 20261027-181508, Oct 27 15:10 to 15:44, 2.77 MB/s): rips/Twine fixed/Twine fixed.mkv, 5.55 GB (the old one 5.21 GB), every audio track 2:08:00.397, packets the same as the PC's: 184,153 video, 240,018 in each AC-3 track, subtitles 1,084/1,102/9/9. # Research

## Dumping PS4/PS5 discs without installing (Oct 26)
Asked again, researched again (GitHub sources read directly; PSDevWiki and archive.org were unreachable):
- No public code does it, for either console. Every dumper reads the running title's PFS mount after an install: EchoStretch's ps5-app-dumper, idlesauce's ps5-self-pager, Itemzflow ("make SURE both discs and ALL Languages are installed"), and Al-Azif's ps-disc-detect (Oct 2026: discs "identified and not dumped").
- Decrypting on a PC needs the per-title key (EKPFS, or the final XTS keys). flatz's pkg_pfs_tool and maxton's LibOrbisPkg/PkgTool decrypt retail PKGs given those keys; deriving them from a rif needs secret keys that are published only as XXXX (and the retail path is compiled out). flatz's writeup: the key "stays inside SM memory and never leaves it". PS5: SvenGDK's LibProsperoPKG documents the FIH format (FIH header | XTS outer PFS | CNT (app_sc) | install archive; a disc splits it into app_0 and app_sc per app.json, app.crc is CRC-32C per 64 KiB) and says the retail image key "is not derivable from public inputs". The rumored PS5 BootROM key leak isn't shown to give PFS or rif keys.
- Not blocked in principle: having the console decrypt in place. The kernel's PFS mount takes the encrypted keys (eekpfs, eekc from the rif, finalized, disc, pubkey_ver, key_ver, sblock_offset...) and the security processor hands back key handles, the same path an installed game uses. Public mounters (ShadowMountPlus, dump_installer, kstuff-lite's pfsc_mount: /dev/lvdctl ioctl C0286D00 then nmount fstype pfs) only ever pass fake/zero keys. Unknowns: the exact options, getting the EKC from a disc rif (npdrm mailbox), whether "disc" means a drive authentication, whether PFSC needs a second mount.
- gasb07/ps4mount (Oct 11, 2026) "installs" a PS4 PKG on a PS5 by reference (a symlink into /user/app, install metadata, sceAppInstUtilAppInstallAll) and plays it from USB without copying; retail PKGs aren't supported. Pointing it at a disc's app.pkg with the disc's rif is an untried experiment. It writes into the console's install database: ask before trying.
- The rif (kstuff-lite npdrm.h): 0x400 bytes, "RIF\0", content ID at 0x20, type/drm/content type at 0x50-0x56, discKey at 0x240, IV at 0x260, an encrypted secret at 0x270; retail and disc rifs decrypt only inside the security processor.
- So for now: install first, as ripper does. The in-place mount is the one real lead.

## Custom drive firmware (for the tester's BP50NB40)
From redumper (d9bd915b), OmniDrive (da01346b, v1.0.4), DiscImageCreator (9269234a) and the MakeMKV forum:
- OmniDrive marks itself in standard INQUIRY: bytes 74-82 "OmniDrive", 83-85 major/minor/patch (ask for 104 bytes). 1.0.4 or newer for DVDs (1.0.3 left DVD reads scrambled after one C0). SpiralDrive puts "SpiralDrive v" at bytes 36-55. A USB bridge that cuts INQUIRY to 36 bytes would hide both.
- OmniDrive's raw read is C0 (12 bytes): byte 1 disc type (0 CD, 1 DVD, 2 BD) | 0x04 raw addressing | 0x08 FUA | 0x10 descramble (DVD/BD); 2-5 start (signed), 6-9 count; byte 10 on CDs: subchannel (1 P-W, 2 Q) | 4 C2. Frames: CD 2352 (+294 C2, +96 sub), DVD 2064 (ID, IED, CPR_MAI, data, EDC; scrambled unless 0x10), BD 2070 in redumper's code (2072 in the README). A read only, by its source.
- Under OmniDrive a Nintendo disc answers plain READ with 05/30/02, and its physical format's layer descriptor starts with FF: that's how redumper tells it.
- LibreDrive has no public detection: MakeMKV is closed. It "allows one to read VID from disc" and "disables bus encryption" (its developer); turned on per session by MakeMKV, not kept in the drive.
- The BP50NB40 is MediaTek MT1959 (redumper lists two hardware kinds, NB50 and NB52). It runs LibreDrive with LG's MK-patched firmware, and OmniDrive by flashing the BU40N 1.00-based image (it then shows as BU40N 1.00). Stock 1.00 is in redumper's list as MediaTek with a 3 MB cache.
- MediaTek cache read: F1 06 <offset> <length>, 0xB00 bytes an entry (main 2352 scrambled, P-W, Q, C2), for CD lead-in/out. Only on listed MediaTek drives: F1 is READ EEPROM on Plextors.
- Raw DVD on stock LG firmware (DIC's ReadDVDRaw, the Nintendo route): A8 08 <lba> 16 (READ(12) with FUA), then 3C 02 00 for 2384 x 16 bytes (scrambled, with ECC). DIC's sheet: the BP50NB40 stalls on READ BUFFER past 3C 0B FF, so no guessing other modes.
- Never: WRITE BUFFER 3B (flashing), 3C 0D 01 on LG (Jamless Play, byte 7 FF saves to flash), FF (TSST flash, Kreon lock), EE (Plextor reset), E7 other than reading memory, SEND KEY format 06 (region), MODE SELECT with save pages.
- The drive test now: INQUIRY to 104 bytes with the OmniDrive/SpiralDrive marks; C0 raw reads only on OmniDrive; F1 only on BP50NB40/BU40N; the stock-LG raw DVD trick only on LG drives; the Nintendo check by the physical format.

## RomM upload API (5.4.x)

## PS5 network and disk writes (found on RommPS #39, Nov 9-10)
- A socket's receive buffer is capped at 512 KB (asks of 1-4 MB granted as 512 KB, 8 MB+ refused); the default is 64 KB. kern.ipc.maxsockbuf and the net.inet.tcp sysctls don't exist, even as root. One connection carries at most 512 KB per round trip.
- Many small pwrite()s from several threads into one file are slow on /data: 8 download threads writing curl's chunks as they came went no faster than one (8.5 MB/s); 1 MB blocks gave ~15 MB/s. A plain single-thread copy on /data runs at ~14 MB/s whether its blocks are 64 KB or 1 MB. For ripper: keep disc writes in big blocks if several threads ever write one image.
- TCP_INFO works but tcpi_rtt runs high (15-34 ms on a 2 ms LAN); time the TCP handshake instead.
